# 真机验证计划（尚未执行）

此文档设计未来的独立实验，不表示已经实现验证程序。第一阶段不实现完整 App。账户门槛不通过时停止 MusicKit 集成；网络独立实验可以不使用 MusicKit，但不能据此进入完整 MVP。

## 准备与证据

主要验收组合固定为用户提供的 iPhone（iOS 26.0）与 iPad Pro 2018（iPadOS 17.4.1），由 iPhone 开启个人热点。记录 iPhone 型号（尚未提供）、双方具体系统构建号、iPad 型号、Apple Music 订阅状态/地区、最终 Bundle ID、签名方式、源码版本、Xcode 版本。不得为测试擅自升级设备；后续系统变化需另记测试组合，不能覆盖原结果。

以真实使用方式开启 iPhone 个人热点，iPad 在 Wi-Fi 中确认连接该热点。双端先前台授予本地网络权限。首轮关闭 VPN 等可能影响路径的因素并记录，后续再覆盖日常配置。正常蜂窝联网要单独确认，音乐流量可能消耗套餐，不购买流量包。

日志包含本地时间、运行 ID、设备角色、前后台事件、连接状态、命令 ID、接收时间、执行结果和播放器状态；分别保存发送与接收日志，比较同一 request ID。音频确实从 iPad 内置扬声器输出需人工听音确认，不能只看 play() 返回。

锁屏实验必须脱离调试器运行；调试器可能改变后台行为。无需 Mac 实时调试，以本地持久化日志和解锁后导出为主。恢复前台后批量出现的命令不能计为锁屏期间已成功执行。日志不要包含令牌、Apple 密码或热点密码；分享前脱敏。

## G0：账户资格（最先核实）

1. 按 FEASIBILITY 的账户步骤，确认免费账户是否可以启用 MusicKit App Service。
2. 若不能，记录阻塞并停止 MusicKit 开发，不购买会员。
3. 若可以，使用最终 AltStore 重签名身份的小型资格实验，分别在两端验证授权和目录查询，在 iPad 验证订阅能力与完整歌曲播放；查询歌曲、专辑、歌单分别留结果。
4. 安装后以及至少一次免费刷新后重复，确认身份或资格没有因重签名变化而失效。

判据：最终安装身份可使用所需服务，有完整播放证据。只有弹窗允许、订阅查询成功、编译成功或播放试听均不够。

## G1：优先验证热点前台双向通信

每种模式做 3 次全新会话，包含重新开热点、重新加入和重启 App；每会话双向各发 100 条小消息（间隔约 1 秒），逐条核对回执。成功条件建议为：10 秒内建立连接，每条消息 3 秒内获得应用层回执、无错序执行/重复执行；阈值是本项目验收标准，不是 Apple 系统保证。

| 测试 | 方法 | 要回答的问题 |
| --- | --- | --- |
| H1 | iPad NWListener 发布 `_musicremote._tcp`，iPhone NWBrowser 发现并连接；includePeerToPeer 关闭 | 热点主路径能否发现并双向传输 |
| H2 | 不浏览，iPhone 手动输入 iPad 候选 IP 和端口 | 发现失败时单播是否仍通 |
| H3 | 反转监听方，iPad 主动连接 iPhone | 是否仅某个连接发起方向可行 |
| H4 | NW 参数启用 includePeerToPeer，重复发现/传输 | 点对点候选是否帮助；与纯热点结果区分 |
| H5 | MultipeerConnectivity 使用 `mr-probe`，前台配对/传输 | 前台对照可否工作；不能用于证明锁屏支持 |
| H6 | 普通 Wi-Fi 重复 H1/H2，作为对照 | 失败是否仅热点出现 |
| H7 | 拒绝本地网络权限，再在设置允许后重试 | 错误是否正确解释及恢复 |
| H8 | 热点重开、地址变化、连接中断后恢复 | 是否可以重连并重新同步状态 |

如果 H1 失败而 H2 成功，记录为发现失败、手动路径可用；H2/H3 都失败则不能把“已加入热点、可上网”当作双向通信成功。需保存 Network.framework 状态与错误。地址不能写死，记录实际候选和最终可达端点。

## G2：iPad 锁屏播放

G0 通过后，资格实验扩展到 ApplicationMusicPlayer：授权后选有完整播放资格的内容，确认 iPad 内置扬声器，配置后台 audio，在前台先播放。

- 按电源键锁屏，不仅是把 App 切后台；连续播放 5、15、30、60 分钟，覆盖至少两次曲目切换。
- 分别测试队列、多首专辑或歌单；验证目录中的项目确实在当前地区可播放。
- 首轮不发送网络心跳，避免把高频流量与播放行为混淆。
- 覆盖队列结束、暂停、音频中断、低电量模式、蜂窝网络暂时不可用后恢复；单独记录失败条件，不自动推断原因。

判据：目标系统实际持续出声及跨曲成功，无调试器干预；官方 API 支持不代替本设备验收。

## G3：锁屏播放中接收新选歌（关键门槛）

使用 G1 中通过的 Network.framework 模式，在播放前建立并配对连接。iPhone 保持前台；iPad 进入锁屏。

在锁屏后 1、5、15、30、60 分钟分别发送新的歌曲、专辑、歌单选择，前后穿插上一首、下一首及状态读取。区分：发送成功、iPad 接收、MusicKit 请求成功、开始播放、iPhone 收到状态回执。每组重复 3 次。

额外做低频使用实验：锁屏 30 分钟无 App 层心跳或遥控操作，随后首次发新选歌。若仅靠持续高频消息可用，不可宣称日常空闲也可靠。需要解释已测条件和耗电。

判据建议：新选择在 5 秒内可听见且有一致的执行/状态记录，无需点亮或解锁 iPad；记录所有超时及延迟。通过仅能说明这些已测条件下可用，不保证无限时长后台服务。

## G4：暂停与断线恢复（不可漏测）

1. 播放中远程暂停，保持锁屏分别等待 1、5、15、30 分钟，再发送 play 和全新选歌；检查是否需要解锁才能处理。
2. 队列自然结束后重复同样等待与恢复。
3. 锁屏播放期间先断开旧 TCP 会话，尝试重新建立；再测试热点关闭/重新开启，分别在播放中和暂停中验证。
4. iPhone 遥控 App 退后台/锁屏后再返回，核对重新连接及队列同步；热点开启不能视为遥控 App 保活。
5. iPad 强制退出、系统重启后记录需要用户重新启动的行为；不预期自动唤醒。重启后首次解锁前也不承诺服务可用。

如果 G3 通过而 G4 失败，结果必须写成“连续播放期间已测条件可遥控，暂停或断线后可能需要解锁恢复”。若用户坚持全程无需碰 iPad，则不满足要求，不能进入声称完整满足需求的 MVP。

## 判定与第二阶段

- G0 失败：没有符合免费约束的 MusicKit 路径，不开发完整 App。
- G1 无任何热点路径通过：主要网络环境不满足，不用普通 Wi-Fi 结果替代。
- G2 失败：播放器基础条件不满足，先排查，不进入 MVP。
- G3 失败：锁屏选歌关键要求不满足，不承诺变更通信协议能解决挂起。
- G4 失败：明确限制与人工恢复方式；只有用户接受范围变化后才能实现受限 MVP。
- 所有关键项通过后才实现完整的搜索、配对、命令处理、状态同步和错误界面；不把短时实验结果写成系统级保证。
